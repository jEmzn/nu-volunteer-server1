เอกสารนี้ตอบรายงานทดสอบ (`รายงานทดสอบระบบ NU Volunteer (Backend).pdf`) ทีละข้อ:
- ตรงตามที่รายงานเขียนหรือไม่ และหลักฐาน
- แก้อะไร ที่ไฟล์ไหน
- ผลทดสอบหลังแก้

**ยังไม่ได้ deploy:**
- server ที่รันอยู่ (`node dist/main.js`) ยังเป็นโค้ดเดิมจนกว่าจะ restart แต่ `dist/` ถูก build ใหม่แล้วระหว่างรัน e2e
- เว็บบน Cloudflare Pages ยังเป็นรุ่นเดิม

**วิธีตรวจ:**
- เทียบกับโค้ด server และเว็บ
- อ่านข้อมูลทดสอบในฐานข้อมูลที่ระบบใช้อยู่ (อ่านอย่างเดียว)
- อ่าน journal ของเครื่อง server
- ตัวที่รันอยู่ตอนทดสอบ (`dist/` 8 พ.ย.) ตรงกับ source ล่าสุด ผลในรายงานจึงเป็นของโค้ดปัจจุบัน

## ผลตรวจและการแก้ทีละข้อ

### ข้อ 1 จอ QR แสดง QR หมดอายุเมื่อขาดการเชื่อมต่อ (Critical): จริง

- **หลักฐาน:** dynamic QR ใช้ได้ 60 วินาที (`QR_LIFETIME_S`) และจอต้องขอ token ใหม่จาก server ทุก 10 วินาที เน็ตหลุดเกิน 60 วินาทีจอจึงค้าง QR ที่ใช้ไม่ได้โดยไม่เตือน
- **ข้อเสนอที่ไม่ทำ:** ข้อเสนอ "ให้ key ไปสร้าง token ที่หน้าเว็บ" ไม่ปลอดภัย เพราะใครได้ `QR_SECRET` จะปลอม QR ได้ทุกกิจกรรม
- **แก้ฝั่ง server:** `POST /activities/:id/qr` (dynamic) คืน `upcoming` คือ token ของ 5 นาทีถัดไป (30 ตัวที่ 10 วินาที หรือ 20 ตัวที่ 15 วินาที) แต่ละตัวใช้ได้เมื่อถึง window ของตัวเองเท่านั้น จึงไม่เปิดช่องให้ใช้ QR ล่วงหน้า (มี test ยืนยัน)
- **แก้ฝั่งเว็บ:** ตอนขอ token ไม่สำเร็จ จอสลับไปใช้ token ล่วงหน้าตามเวลา server แสดง "ออฟไลน์ QR นี้ใช้ได้อีก N นาที" และเมื่อ token หมดจะซ่อน QR พร้อมข้อความ "QR หมดอายุ รอเชื่อมต่ออินเทอร์เน็ต"
- **ผล:** จอทนเน็ตหลุดได้ราว 6 นาที (token ล่วงหน้า 5 นาที บวกอายุ 60 วินาทีของตัวสุดท้าย)
- **ไฟล์:** `src/modules/qr/qr.ts`, `qr-token.ts` / เว็บ `src/lib/qr.ts`, `src/screens/sup/useQrFeed.ts`, `QrScreen.tsx`, `QrPanel.tsx`, `QrCode.tsx`

### ข้อ 2 session ผู้ดูแลหมดอายุระหว่างงาน (Critical): จริง

- **หลักฐาน:** token ผู้ดูแลอายุ 12 ชั่วโมง (`auth.ts`)
- **แก้:** ขยายเป็น 7 วัน
- **ข้อแลกเปลี่ยน:** token ที่หลุดไปจะใช้ได้นานขึ้น และยกเลิก token ได้ทางเดียวคือเปลี่ยน `JWT_SECRET` (เหมือนเดิม)
- **ไฟล์:** `src/modules/auth/auth.ts`

### ข้อ 3 QR หมดอายุระหว่างนิสิตใหม่กรอกข้อมูล (High): จริง

- **หลักฐาน:** ตอนออนไลน์เว็บไม่ส่งเวลาที่เปิดลิงก์ server จึงตรวจ QR กับเวลาที่กดส่ง กรอกเกิน 60 วินาทีก็ได้ `QR_EXPIRED` e2e เดิมก็ทดสอบพฤติกรรมนี้อยู่
- **แก้ฝั่งเว็บ:** ส่ง `scannedAt` = เวลาที่เปิดลิงก์มากับทุก claim (เมื่อหน้าเว็บวัดเวลา server ได้แล้ว) และรีเซ็ตเวลานี้เมื่อสแกน QR ใหม่ในแท็บเดิม
- **แก้ฝั่ง server:** ธง `offline` ("ส่งภายหลัง") ติดเมื่อเครื่องบอกว่าเป็นสแกนที่เก็บไว้ตอนออฟไลน์ (`offline: true` ซึ่งเว็บส่งจากคิว) หรือส่งช้ากว่าเวลาเปิดลิงก์เกิน 3 นาที ป้าย "ส่งภายหลัง" ที่รายงานระบุว่าผ่านจึงยังทำงานเหมือนเดิม
- **ไฟล์:** `src/modules/claims/claims.ts` / เว็บ `src/screens/claim/Claim.tsx`, `src/lib/pending.ts`, `src/data/remote.ts`, `src/data/api.ts`

### ข้อ 4 สแกนที่ส่งภายหลังถูกติดธงนอกพื้นที่ทุกครั้ง (High): อาการจริง สาเหตุไม่ตรงกับที่รายงานเขียน

- **หลักฐาน:** แถวของกิจกรรม `j64lp88f4a` มี `accuracy = 99` แต่ไม่มีระยะ server บันทึก accuracy เฉพาะเมื่อได้ lat/lng จากมือถือแล้ว แปลว่ามือถือส่งพิกัดมาครบ
- **สาเหตุจริง:** QR token ไม่มีพิกัดของจอ เพราะกิจกรรมนี้ใช้ static QR ที่ได้มาตอนจอยังไม่มี GPS
- **online กับ offline ใช้กฎเดียวกัน:** ทั้งสองทางใช้ `judgeLocation()` ตัวเดียวกัน ส่วนผลที่วัดได้ 1.4 ม. ตามรายงานไม่พบในข้อมูล
- **แก้ฝั่ง server:** พิกัดใน token ไม่ขึ้นกับ GPS ของจออย่างเดียวแล้ว
  - static ใช้สถานที่ของกิจกรรม (`lat`/`lng`) ก่อน เพราะ QR ที่พิมพ์มักพิมพ์ที่สำนักงาน
  - dynamic ใช้พิกัดจอก่อน แล้วค่อยใช้ของกิจกรรม
- **แก้ฝั่งเว็บ:** ถ้าเป็น static แต่จอยังไม่ได้ตำแหน่งและกิจกรรมไม่ได้ปักหมุด หน้าจอเตือนข้างปุ่มดาวน์โหลด/พิมพ์
- **ไฟล์:** `src/modules/qr/qr.ts` / เว็บ `src/screens/sup/QrScreen.tsx`

### ข้อ 5 dynamic QR รับชั่วโมงนอกเวลากิจกรรม (Medium): จริง

- **หลักฐาน:** มีแถวจริงที่สแกนได้ตอน 23:57 ก่อนกิจกรรมเริ่ม 00:00 เพราะ `checkTime()` ตรวจช่วงเวลาเฉพาะ static
- **แก้:** ใช้ช่วงเริ่ม − 30 นาที ถึงจบ + 30 นาที กับ QR ทั้งสองแบบ
- **ข้อแลกเปลี่ยน:** กิจกรรมที่จบเกินเวลาเกิน 30 นาที ผู้ดูแลต้องเพิ่มชั่วโมงให้เอง
- **ไฟล์:** `src/modules/qr/qr-token.ts`

### ข้อ 6 หน้าแรกนิสิตไม่อัปเดตเมื่อมีกิจกรรมใหม่ (Medium): จริงบางส่วน

- **หลักฐาน:** หน้าแรกโหลดใหม่ทุก 60 วินาทีและทุกครั้งที่กลับมาที่แท็บ ตามที่ตั้งใจไว้ใน SPEC 9.3 จึงอัปเดตเองภายใน 1 นาทีอยู่แล้ว
- **ทำไมไม่ใช้ห้องที่มีอยู่:** ข้อเสนอให้ใช้ห้อง `activities` อันตรายในวันงาน เพราะห้องนี้ได้สัญญาณทุกครั้งที่มีคนสแกน (ตัวนับเปลี่ยน) นิสิต 600 คนจะโหลดใหม่ทุกการสแกน
- **แก้:** เพิ่มห้อง `catalog` ที่ได้สัญญาณเฉพาะตอนสร้างหรือแก้กิจกรรม หน้าแรกนิสิตฟังห้องนี้ แล้วรอสุ่ม 0–3 วินาทีก่อนโหลดรายการกิจกรรม เพื่อไม่ให้ทุกเครื่องยิงพร้อมกัน ข้อนี้ต่างจาก SPEC 9.3 บันทึกไว้ใน README แล้ว
- **ไฟล์:** `src/modules/realtime/realtime.ts`, `src/modules/activities/activities.ts` / เว็บ `src/data/remote.ts`, `src/data/mine.ts`

### ข้อ 7 ธง "อยู่นอกพื้นที่" ใช้กับกรณีไม่มีตำแหน่ง (Medium): จริง

- **หลักฐาน:** server แยกสองกรณีได้อยู่แล้ว มีระยะคืออยู่ไกล ไม่มีระยะคือไม่ได้ตำแหน่ง แต่หน้ารายชื่อและ Excel แสดง "อยู่นอกพื้นที่" ทั้งสองกรณี
- **แก้:** ถ้าไม่มีระยะให้แสดง "ไม่มีตำแหน่ง" แทน ทั้งหน้ารายชื่อและ Excel ไม่ต้องแก้ server
- **ไฟล์:** เว็บ `src/lib/roster.ts` (`locationNote`), `src/screens/sup/Roster.tsx`, `src/lib/excel.ts`

### ข้อ 8 แจ้งเตือนไม่ตรงกับชั่วโมงล่าสุด (Low): จริง

- **หลักฐาน:** ในฐานข้อมูล แลกขวดรอบสองได้ 5 ชม. แต่มี notice แค่ "ได้รับ 2 ชั่วโมง" เพราะแลกขวดแจ้งเฉพาะตอนชั่วโมงเปลี่ยนจาก 0 และการแก้ชั่วโมงรายคนไม่แจ้งเลย
- **แก้:** แจ้ง "ชั่วโมงเปลี่ยนเป็น X ชั่วโมง" ทุกครั้งที่ชั่วโมงเปลี่ยน ทั้งแก้ชั่วโมงและแลกขวด (ถ้าเดิมเป็น 0 แจ้ง "ได้รับ X ชั่วโมง" เหมือนเดิม) ชั่วโมงไม่เปลี่ยนไม่แจ้ง
- **ไฟล์:** `src/modules/claims/credit-writer.ts` (`hoursChangedNotice`), `src/modules/roster/roster.ts`

### ข้อ 9 กรอกรหัสนิสิตคนอื่นแล้วเห็นชื่อเต็ม (Low): จริง และเคยบันทึกเป็นความเสี่ยงไว้แล้ว

- **แก้ (ตามที่เจ้าของโปรเจกต์สั่ง เป็นมาตรการชั่วคราวก่อนมี SSO):** `/auth/student` ของรหัสที่มีอยู่แล้วคืนชื่อแบบปิดบางส่วน
  - คำแรกแสดงเต็ม คำต่อไปแสดงไม่เกิน 3 ตัวอักษรและไม่เกินครึ่งคำ เช่น "วอเมด เทสเทส" เป็น "วอเมด เทส•••" และ "สมชาย ใจดี" เป็น "สมชาย ใจ•••"
  - นับตัวอักษรไทยทั้งพยัญชนะพร้อมสระและวรรณยุกต์ จึงไม่ตัดสระออกจากพยัญชนะ
  - ไม่ส่ง `reminders`/`notify` ของคนนั้นด้วย
- **ฝั่งเว็บ:** หลังกด "ใช่" หน้ารับชั่วโมงโหลดชื่อเต็มของตัวเองด้วย token ของตัวเอง เครื่องจึงไม่เก็บชื่อที่ปิดไว้
- **ข้อจำกัด:** ชื่อเต็มยังอยู่ใน payload ของ token ที่ได้กลับมา และใครรู้รหัสก็ยังเข้าเป็นนิสิตคนนั้นได้ มาตรการนี้กันได้เฉพาะการดูจากหน้าจอ แก้จริงต้องใช้ SSO
- **ไฟล์:** `src/common/format.ts` (`maskName`), `src/modules/auth/auth.ts` / เว็บ `src/screens/claim/Claim.tsx`

### ข้อ 10 นิสิตเข้าถึง deviceId และธงของทุกคน (Low): จริงบางส่วน

- **หลักฐาน:** `deviceId`, `distance`, `accuracy` ของคนอื่นถูกตัดออกอยู่แล้ว แต่ยังส่ง `flags`, `reason` (เหตุผลที่ลดชั่วโมง), `editedBy`, `ref` และ `items`
- **แก้:** แถวของคนอื่นเหลือแค่ `studentId`, `name`, `hours`, `fullHours`, `at` และ `method` ซึ่งหน้าเว็บนิสิตใช้ครบ
- **ไฟล์:** `src/common/mappers.ts`

## ความพร้อมก่อนวันงาน

- **HTTP 530 ตอน 03:16 และ 03:26:**
  - journal ของเครื่อง server บันทึกว่า Wi-Fi หลุดช่วง 03:00–03:02 (`ssid-not-found`)
  - เวลา 03:16 และ 03:26 ยืนยันไม่ได้ เพราะ cloudflared รันในเทอร์มินัลและ log ไม่ได้ถูกเก็บ
  - แนะนำให้ใช้สายแลน ทำ cloudflared และ API เป็น systemd service (`DEPLOY-CLOUDFLARE-TODO.md` ขั้นที่ 5) และปิดโหมดพักเครื่อง
- **"ลิมิต 100,000 request ต่อวัน":** เป็นเพดานของ Cloudflare Workers ไม่เกี่ยวกับ Tunnel ส่วนหน้าเว็บบน Pages เป็นไฟล์ static
- **limit ต่อ IP:** claim นับต่อนิสิต ไม่ใช่ต่อ IP นิสิตที่ใช้ Wi-Fi เดียวกันจึงไม่แย่งโควต้ากัน แต่การขอ QR นับรวมต่อชื่อผู้ดูแลที่ 60 ครั้งต่อนาที จอหนึ่งใช้ 6 ครั้งต่อนาที ถ้าเปิดเกิน 10 จอด้วยชื่อผู้ดูแลเดียวกันจะโดน 429 ให้ใช้ชื่อต่างกันต่อจอ
- **ทดสอบกับมือถือจริง:** หลัง deploy ควรทดสอบซ้ำบนมือถือ (Android Chrome, iPhone Safari, เปิดจาก LINE) โดยเฉพาะการตัดเน็ตจอ QR 2–3 นาที

## ข้อจำกัดที่ยังเหลือ

- **ข้อ 9 ก่อนมี SSO:** ชื่อเต็มยังอยู่ใน token และใครรู้รหัสก็ยังเข้าเป็นนิสิตคนนั้นได้
- **ธง "ส่งภายหลัง":** คนที่ปลอม `scannedAt` ย้อนหลังไม่เกิน 3 นาทีและไม่ส่ง `offline: true` จะไม่ติดธง (เดิมย้อนได้ถึง 48 ชั่วโมงโดยติดธง ซึ่งยังเป็นแบบนั้นถ้าเกิน 3 นาที)
- **token ล่วงหน้าบนจอ:** ใครมี token ผู้ดูแลก็ขอ QR ของ 5 นาทีข้างหน้าได้ แต่ก็ขอ QR ปัจจุบันได้อยู่แล้ว ความเสี่ยงจึงเท่าเดิม และ token ล่วงหน้าใช้ได้เฉพาะเมื่อถึงเวลาของมัน
- **token ผู้ดูแล 7 วัน:** ถ้าเครื่องผู้ดูแลหาย token ใช้ได้นานขึ้น ยกเลิกได้ทางเดียวคือเปลี่ยน `JWT_SECRET`
- **ยังไม่ได้ทดสอบบนมือถือจริงและ domain จริง** หลังแก้

## ขั้นตอน deploy (รออนุมัติ)

1. server: `npm run build` (ทำแล้วระหว่างรัน e2e) แล้ว restart `node dist/main.js`
2. เว็บ: build และ deploy ขึ้น Cloudflare Pages
   - server ใหม่ใช้กับเว็บเดิมได้ (field ใหม่เป็นแบบไม่บังคับ)
   - แต่ข้อ 1, 3, 6, 7 จะเห็นผลเมื่อเว็บใหม่ขึ้นแล้ว
3. ทดสอบซ้ำบน domain จริงตามข้อ 1, 3, 5, 8, 9, 10
