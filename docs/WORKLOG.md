## 6 พ.ย. 2569: วัดว่าเครื่องพัฒนารับนิสิต 600 คนได้ไหม

เจ้าของโปรเจกต์ถามว่าเครื่องนี้รองรับ 600 คนที่เข้าใช้ช่วงไล่เลี่ยกันได้ไหม จึงจำลองด้วยสคริปต์ Node กับ `dist/main.js` และ PostgreSQL ชั่วคราว ใช้ rate limit ค่าเริ่มต้น ตัวจำลองรันบนเครื่องเดียวกัน จึงไม่มีเครือข่ายคั่นกลาง

เครื่อง: Core i5-10400F (6 คอร์ 12 เธรด), RAM 16 GB, NVMe SSD, การ์ดแลนเชื่อมต่อที่ 100 Mbps

| สถานการณ์ | ผล |
| --- | --- |
| A. ใช้ครั้งแรก 600 คนใน 60 วินาที: login, เปิดแอป 6 คำขอ, โปสเตอร์ 20 ใบ | 16,200 คำขอ ตอบ 200 ทั้งหมด p95 ไม่เกิน 83 ms, API ใช้ CPU 72% ของ 1 คอร์, **ส่งออก 3.5 GB** |
| B. เปิดแอปซ้ำพร้อมกัน 600 คนใน 10 วินาที | p95 ไม่เกิน 73 ms ส่งออก 7 MB |
| C. เช็คชื่อ 600 คนใน 60 วินาที กิจกรรมเดียว พร้อมจอผู้ดูแลโหลดรายชื่อทุก 200 ms | p95 117 ms, credits = 600, `credit_count` = 600 |
| D. เช็คชื่อ 600 คนใน 10 วินาที | p95 82 ms, credits = 600 |
| หน่วยความจำ API สูงสุด | 254 MB |

**สรุป:** CPU, ฐานข้อมูลและหน่วยความจำเหลือมาก ข้อจำกัดคือแบนด์วิดท์ขาออกตอนโหลดโปสเตอร์ครั้งแรก (ประมาณ 6 MB ต่อคน ถ้าโหลดครบ 20 ใบขนาดเต็ม) ที่ 100 Mbps ต้องใช้อย่างน้อยราว 5 นาทีสำหรับ 3.5 GB

ข้อจำกัดของการวัด: CPU ของ PostgreSQL ในสถานการณ์ C อ่านไม่ได้ เพราะโปรเซสย่อยปิดไประหว่างวัด และตอนเริ่มวัดยังมี `npm run stack` ของเจ้าของโปรเจกต์เปิดอยู่

## 6 พ.ย. 2569: นับสิทธิ์ที่ server ที่เดียว และให้ admin ศูนย์คืนสิทธิ์

เจ้าของโปรเจกต์เลือกให้ admin ศูนย์คืนสิทธิ์ และให้แก้เรื่องที่กฎนับสิทธิ์อยู่สองที่ ยังไม่ commit ทั้งสองโปรเจกต์

### สิ่งที่แก้

**กฎอยู่ที่เดียว:** `listStrikes()` ใน `src/modules/roster/strikes.ts` ใช้ทั้งตอนตรวจการลงทะเบียน และส่งให้หน้าเว็บผ่าน `GET /students/:id/strikes`

| ฝั่ง | ก่อน | หลัง |
| --- | --- | --- |
| Server | `countStrikes` ตรวจตอนลงทะเบียน | `listStrikes` ตรวจตอนลงทะเบียน และเป็นที่มาของ endpoint |
| Web | `strikesOf`, `creditsLeft`, `semesterStart/End/Number`, `STRIKE_LIMIT` นับเอง | ลบทั้งหมด อ่าน `strikes` จาก `useMine` ที่โหลดมาพร้อมข้อมูลอื่น |

**คืนสิทธิ์:**
- `PATCH /activities/:id/registrations/:studentId` ส่ง `{ waived }` ใช้ได้เฉพาะ admin
- รับเฉพาะรายการที่ถูกหักในภาคนี้ (409 `NOT_A_STRIKE`) จึงคืนล่วงหน้าให้การลงทะเบียนที่ยังไม่ถึงวันไม่ได้
- ไม่ติดกฎล็อก เพราะสิทธิ์ถูกหักหลังกิจกรรมจบ
- ผู้คืนสิทธิ์อยู่ใน audit log เท่านั้น เพราะแก้โครงสร้างตารางไม่ได้

**หน้าจอ:**
- หน้า "บัญชี" ของ admin มีปุ่ม "คืนสิทธิ์ยกเลิกให้นิสิต" เปิด `WaiveSheet.tsx` พิมพ์รหัสนิสิต เห็นสิทธิ์คงเหลือและรายการ แล้วกด "คืนสิทธิ์" หรือ "ยกเลิกการคืน" ผู้ดูแลทั่วไปไม่เห็นปุ่มนี้
- ข้อความฝั่งนิสิต:
  - ป๊อปอัปสิทธิ์หมด: "ส่งข้อความถึงผู้ดูแลกิจกรรมนั้นเพื่อขอคืนสิทธิ์" เปลี่ยนเป็น "ติดต่อผู้ดูแลศูนย์เพื่อขอคืนสิทธิ์"
  - หน้าโปรไฟล์: "แจ้งเหตุผลกับผู้ดูแล" (ลิงก์ไปข้อความส่วนตัว) เปลี่ยนเป็น "ขอคืนสิทธิ์ได้ที่ผู้ดูแลศูนย์" (ลิงก์ไปหน้ากิจกรรม)

## 6 พ.ย. 2569: ย้ายกฎหักสิทธิ์มาตรวจที่ server

ทำตาม 2 เรื่องในแผนงานข้อ 4 ที่เจ้าของโปรเจกต์เลือก ยังไม่ commit ทั้งสองโปรเจกต์

### สิ่งที่แก้

| นิสิตลงทะเบียนเมื่อ | เดิม | ตอนนี้ |
| --- | --- | --- |
| ถูกหักสิทธิ์ครบ 3 ครั้งในภาคนี้ | `ok` | 409 `REG_NO_CREDITS` |
| เคยยกเลิกกิจกรรมนี้หลังกำหนด | `ok` และ `late: true` ค้าง | 409 `REG_LATE_CANCELLED` |

- ไฟล์หลัก: `src/modules/roster/strikes.ts` (ใหม่) กฎตรงกับ `strikesOf()` ของหน้าเว็บ ใช้ `TZ_DISPLAY` หาวันเริ่มภาค
- การนับเป็นแค่ตัวตรวจ หน้าเว็บยังนับเองเพื่อแสดงผล จึงมีกฎ 2 ที่ ถ้าแก้ต้องแก้พร้อมกัน มีเคส E2E ตรวจว่านับตรงกัน และบันทึกใน `CLAUDE.md` แล้ว
- ไม่กระทบคนที่ลงทะเบียนอยู่แล้ว (`already`), การยกเลิก, ผู้ดูแลเพิ่มคนเอง และ walk-in จากการสแกน
- `late: true` ที่ค้างหลังลงซ้ำจะไม่เกิดอีก เพราะลงซ้ำไม่ได้แล้ว และการเพิ่มโดยผู้ดูแลหรือ walk-in ล้างค่านี้อยู่แล้ว
- หน้าเว็บไม่ต้องแก้โค้ด ข้อความจาก 409 แสดงได้จากงานรอบก่อน

**กรณีหน้าค้าง:** ถ้านิสิตเปิดหน้าไว้แล้วยกเลิกครั้งที่ 3 จากอีกเครื่อง ปุ่มยังเป็น "ลงทะเบียน" เมื่อกดจะถูกปฏิเสธ เห็นเหตุผล แล้วปุ่มเปลี่ยนเป็น "ลงทะเบียนไม่ได้" E2E รอบแรกล้ม 1 เคสเพราะเทสต์คาดว่าปุ่มเปลี่ยนเองก่อนกด ตรวจจากภาพหน้าจอแล้วจึงแก้เทสต์ให้กดจริง

### พบระหว่างทำ (แก้แล้วในหัวข้อด้านบน)

**ไม่มีช่องทางคืนสิทธิ์:** หน้าเว็บบอกนิสิตว่า "ส่งข้อความถึงผู้ดูแลกิจกรรมนั้นเพื่อขอคืนสิทธิ์" แต่ไม่มี endpoint ตั้งค่า `waived` ผู้ดูแลจึงคืนสิทธิ์ไม่ได้ ตอนนี้ต้องแก้ในฐานข้อมูลโดยตรง เมื่อ server บังคับกฎแล้ว นิสิตที่สิทธิ์หมดจะลงทะเบียนไม่ได้จริงจนกว่าจะขึ้นภาคใหม่

## 6 พ.ย. 2569: ส่งโปสเตอร์เป็น URL และให้ `POST /credits` รับ `reason`

ทำตามแผนงานข้อ 1 และ 2 ด้านล่าง ยังไม่ commit ทั้งสองโปรเจกต์

### 1. โปสเตอร์

- `GET /activities` และ `GET /activities/:id` ส่งรูปที่อัปโหลดเป็น `/activities/:id/poster?v=<เวอร์ชัน>` รูปในตัวเว็บและค่าว่างเหมือนเดิม
- เพิ่ม `GET /activities/:id/poster` ส่ง JPEG พร้อม `ETag` และแคช 1 วัน รับเข้าและเก็บในฐานข้อมูลเหมือนเดิม ไม่แก้โครงสร้างตาราง
- Web: `remote.ts` เติมที่อยู่ของ API ให้จุดเดียว และไม่ส่ง `poster` กลับถ้ายังเป็น URL เดิม ทุก `<img>` จึงไม่ต้องแก้
- เทมเพลตยังส่งตัวรูปเหมือนเดิม

**เปลี่ยนจากแผน:** แผนเดิมใช้ `md5(poster)` เป็นเวอร์ชัน แต่วัดแล้วแพงเกินไป จึงใช้ขนาดไฟล์กับ md5 ของ 8 KB แรก

| โปสเตอร์ 300 KB จำนวน 100 ใบ | เวลาใน SQL ต่อครั้ง | JSON |
| --- | --- | --- |
| `SELECT *` (เดิม) | 152 ms | 39 MB |
| `md5(poster)` (แผนเดิม) | 84 ms | 0.01 MB |
| ขนาด + md5 ของ 8 KB แรก (ที่ใช้) | 6.4 ms | 0.01 MB |

**ข้อแลกเปลี่ยน:** รูปสองใบที่ขนาดเท่ากันทุกไบต์และ 8 KB แรกเหมือนกันจะได้เวอร์ชันเดียวกัน เบราว์เซอร์อาจแสดงรูปเก่าได้ไม่เกิน 1 วัน แล้วจะตรวจ `ETag` และได้รูปใหม่ โอกาสเกิดต่ำมาก จึงไม่ใช้แคชแบบ `immutable`

**ผลวัดผ่าน HTTP จริง** (`dist/main.js` กับ PostgreSQL บนเครื่องเดียวกัน ไม่มีความหน่วงของเครือข่าย)

| รายการ | ผล |
| --- | --- |
| `GET /activities` โปสเตอร์ 20 ใบ | 10.5 KB, 4.6 ms (เดิมประมาณ 8 MB) |
| `GET /activities` โปสเตอร์ 100 ใบ | 52.8 KB, 10.4 ms |
| `GET /activities` พร้อมกัน 50 คำขอ รวม 300 ครั้ง โปสเตอร์ 100 ใบ | median 120 ms, p95 240 ms |
| รูป 1 ใบ | 300 KB, 5.5 ms |
| รูป พร้อมกัน 50 คำขอ รวม 300 ครั้ง | median 108 ms, p95 149 ms |
| รูปที่เบราว์เซอร์มีแล้ว (`If-None-Match`) | 304, 0 ไบต์ |

### 2. `POST /activities/:id/credits` รับ `reason`

- บันทึกชั่วโมงกับเหตุผลใน transaction เดียว ชั่วโมงไม่เต็มแต่ไม่มีเหตุผลได้ 400 และไม่เขียนอะไรเลย **ผู้เรียก API ต้องส่ง `reason` เพิ่ม**
- Web: `EditHoursSheet.tsx` เรียกคำสั่งเดียว ถ้าได้ `already` จะแก้ด้วย `PATCH` ต่อ เพื่อให้ค่าที่ผู้ดูแลเลือกถูกบันทึก ทั้งกรณีผู้ดูแลอีกคนให้ชั่วโมงไปก่อนและการกดซ้ำหลังคำตอบหาย

## 5 พ.ย. 2569: ตรวจกฎลงทะเบียนที่ server

### สิ่งที่แก้

| เรื่อง | เดิม | ตอนนี้ |
| --- | --- | --- |
| ลงทะเบียนก่อน `opensAt` | `ok` | 409 `REG_NOT_OPEN` |

**1. ~~ส่งโปสเตอร์เป็น URL แทนตัวรูป~~ เสร็จแล้ว**

เจ้าของโปรเจกต์ยืนยันว่าแทบทุกกิจกรรมอัปโหลดรูปเอง ปัญหาจึงเกิดจริง ไม่ใช่กรณีสุดโต่ง และรายการโตตามจำนวนกิจกรรมสะสม

- Server: เพิ่ม `GET /activities/:id/poster` แบบ `@Public()` ส่ง JPEG พร้อม `ETag` และ `Cache-Control`
- Server: `GET /activities` และ `GET /activities/:id` ส่ง `poster` เป็น `/activities/:id/poster?v=<md5>` เมื่อเป็นรูปที่อัปโหลด ส่วนรูปสำเร็จรูปยังเป็น path เดิม
- Web: `remote.ts` เติม `API_URL` ให้ path นี้จุดเดียว ทุก `<img src={a.poster}>` จึงไม่ต้องแก้
- Web: `toEdit` ไม่ส่ง `poster` ถ้าผู้ดูแลไม่ได้เปลี่ยนรูป เพราะ `assertPoster` จะปฏิเสธ URL
- เทมเพลตยังส่งตัวรูปเหมือนเดิมในรอบแรก เพราะโหลดเฉพาะผู้ดูแล และ `applyTemplate` ต้องคัดลอกตัวรูปไปกิจกรรมใหม่
- ไม่แก้โครงสร้างตาราง ตามข้อ 11 จึงใช้ `md5(poster)` เป็นเวอร์ชันแทนคอลัมน์ใหม่ (ตอนทำจริงเปลี่ยนเป็นขนาดกับ md5 ของ 8 KB แรก)
- ทดสอบ: ขนาดรายการก่อนและหลัง, 304 จาก `ETag`, แก้กิจกรรมโดยไม่เปลี่ยนรูปแล้วรูปเดิมยังอยู่, เปลี่ยนรูปแล้ว URL เปลี่ยน, E2E ครบ และ k6

**2. ~~ให้ `POST /credits` รับ `reason`~~ เสร็จแล้ว**

รับ `reason` และบังคับเมื่อชั่วโมงไม่เต็ม ให้เขียนใน transaction เดียวกับ credit แล้วลดการเรียก 2 คำสั่งใน `EditHoursSheet.tsx` เหลือคำสั่งเดียว แก้ `API-CONTRACT.md` ด้วย

**3. ทดสอบกล้องจริงบนมือถือ**

`getUserMedia` ใช้ได้เฉพาะ HTTPS หรือ localhost การเปิดผ่าน `STACK_HOST` ด้วย http จึงเปิดกล้องไม่ได้ ต้องทดสอบผ่าน HTTPS tunnel หรือบนเครื่องทดสอบที่มี HTTPS โดยตั้ง `WEB_ORIGIN`, `CORS_ORIGINS` และ `VITE_API_URL` ให้ตรงกัน

**4. เรื่องที่เจ้าของโปรเจกต์ต้องตัดสินใจ**

### ข้อสังเกตจากการทดสอบร่วม (รอตัดสินใจ ไม่ได้แก้)

ทดลองเรียก API ตรงแล้วได้ผลตามนี้ หน้าเว็บกันไว้ให้ แต่ server ไม่กัน ต้นแบบก็เป็นแบบเดียวกัน จึงเป็นการตัดสินใจเรื่องกติกา ไม่ใช่บั๊ก

| เรื่อง | ผลที่ได้จริง |
| --- | --- |
| ลงทะเบียนก่อน `opensAt`, ลงทะเบียนกิจกรรมที่ `hidden`, ลงทะเบียนหลังกิจกรรมจบ | `{ result: "ok" }` ทั้งหมด (แก้แล้ว 5 พ.ย. 2569 ได้ 409) |
| ลงทะเบียนหลังหักสิทธิ์ครบ 3 ครั้ง, ลงทะเบียนซ้ำหลังยกเลิกช้า | `{ result: "ok" }` ทั้งคู่ (แก้แล้ว 6 พ.ย. 2569 ได้ 409) |
| แถวลงทะเบียนหลังลงซ้ำจากการยกเลิกช้า | ยังมี `late: true` ทั้งที่ใช้งานอยู่ หน้าเว็บนับสิทธิ์จากแถวที่ `cancelledAt` เท่านั้น จึงยังไม่กระทบ (ไม่เกิดอีกแล้ว 6 พ.ย. 2569 เพราะลงซ้ำไม่ได้) |

| ผู้ดูแลหน่วยงานอื่นอ่านแชท | 200 แต่เขียนไม่ได้ (403) |
