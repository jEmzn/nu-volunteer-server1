### claim แบบ burst (1000 คนต่อรอบ)

สคริปต์เดียวกับรอบ 7 พ.ย. (`shared-iterations`, `CONC` VU ยิงต่อกัน) รอบนี้วัดความเร็วจากเวลาช่วงยิง claim ที่ k6 แสดงในแถบ `scan` ไม่ได้ใช้ `iterations/s`

| CONC | ทาง | p95 | avg | ล้มเหลว | เวลายิง 1000 claim | claim ต่อวินาที | RESULT |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | named tunnel | 1.34 s | 1.18 s | 0 | 12.6 s | ~79 | ตรง |
| 200 | named tunnel | 2.75 s | 2.28 s | 0 | 12.9 s | ~78 | ตรง |
| 300 | named tunnel | 3.65 s | 3.08 s | 0 | 12.1 s | ~83 | ตรง |
| 400 | named tunnel | 4.85 s | 3.79 s | 0 | 11.9 s | ~84 | ตรง |

### สรุป

1. **named tunnel ไม่มีเพดาน 200 request ค้างพร้อมกัน** ที่ 300 และ 400 ไม่มี 429 เลย ส่วน quick tunnel ที่ 300 โดน 429 ไป 79% (หัวข้อ 7 พ.ย.) ตรงกับเอกสารของ Cloudflare ที่ระบุเพดาน 200 ไว้เฉพาะ quick tunnel
2. **tunnel แทบไม่เป็นคอขวดแล้ว** ผ่าน tunnel ได้ราว 83 ต่อวินาที ยิงตรงได้ราว 87 ต่างกันราว 5%
3. **คอขวดที่เหลืออยู่ที่ server ราว 85 claim ต่อวินาที** เวลารอขึ้นกับความยาวคิว เช่น 400 คนกดพร้อมกัน คนสุดท้ายรอราว 5 วินาที ไม่มี error และข้อมูลตรงทุกรอบ ส่วนเกณฑ์ p95 < 500 ms ยังผ่านเฉพาะตอนคนทยอยสแกน
4. **Cloudflare ไม่ได้ขวาง load test** Security > Events ช่วง 19:35–19:41 ไม่มี event ของการทดสอบ มีแค่ bot จากต่างประเทศมาสุ่มหา `/wp-config.php` บน `volunteerapp` เวลา 16:47 ซึ่ง Cloudflare Managed Free Ruleset บล็อกไว้ เป็นการสแกนหาช่องโหว่ตามปกติของอินเทอร์เน็ต ไม่เกี่ยวกับการทดสอบ
5. **แก้ตัวเลขของรอบ 7 พ.ย.** ที่เคยสรุปว่า server รับได้ 60 และผ่าน tunnel เหลือ 40 claim ต่อวินาทีนั้นผิด แก้ไว้ในหัวข้อนั้นแล้ว

### แผน CSP และ token ใน `localStorage` (ข้อ 6, ทำข้อ 1 และ 3 แล้ว 8 พ.ย. 2569)

ปัญหา: เว็บเก็บ token ใน `localStorage` ซึ่ง JavaScript ทุกตัวบนหน้าอ่านได้ ถ้าวันหนึ่งมีช่องให้คนอื่นฝังสคริปต์ลงหน้าเว็บได้ (XSS) สคริปต์นั้นจะส่ง token ออกไป แล้วคนร้ายใช้ token เป็นนิสิตคนนั้นได้ 30 วัน หรือเป็นผู้ดูแลได้ 12 ชั่วโมง ตอนนี้ยังไม่พบช่อง XSS (React escape ข้อความให้เอง และจุดเดียวที่ใส่ HTML ตรงคือ SVG ที่ library `qrcode` สร้าง) แต่ยังไม่มี CSP ไว้กันอีกชั้น

1. **ทำแล้ว:** `vite build` สร้าง `dist/_headers` ให้เอง (plugin ใน `nu-volunteer-web/vite.config.ts`) Cloudflare Pages อ่านไฟล์นี้แล้วใส่ header ให้ทุกไฟล์ ที่อยู่ API ในนโยบายมาจาก `VITE_API_URL` ตอน build จึงไม่ต้องแก้ domain เอง นโยบายคือ `script-src 'self'` (รันได้เฉพาะสคริปต์ของเราเอง), `style-src 'self' 'unsafe-inline'` (React และ motion ใส่ `style=""` ตรง), รูปและการเชื่อมต่อได้เฉพาะเว็บเองกับ API, `frame-ancestors 'none'` และเพิ่ม `X-Content-Type-Options`, `Referrer-Policy`
2. **ยังต้องทำตอนขึ้นจริง:** ตอนนี้ `_headers` ใช้ `Content-Security-Policy-Report-Only` (รายงานใน Console แต่ไม่บล็อก) ขึ้นไปแล้วให้เปิดทุกหน้าบนมือถือจริง โดยเฉพาะกล้องสแกนซึ่ง e2e ไม่ได้ทดสอบ ถ้าใน Console ไม่มีข้อความ CSP ให้เปลี่ยน `PAGES_CSP_HEADER` ใน `vite.config.ts` เป็น `Content-Security-Policy` แล้ว build ใหม่
3. **ทำแล้ว:** `vite preview` ใส่ CSP แบบบล็อกจริง และ e2e ทุกตัวรันบน preview โดยถือว่า console error เป็นความล้มเหลวอยู่แล้ว จึงไม่ต้องเพิ่ม test ใหม่ ถ้าหน้าไหนโดนบล็อก test ของหน้านั้นจะ fail ผล: `npm run e2e` ผ่าน 71/71 (ต้องตั้ง `RATE_WRITES` สูงใน `scripts/e2e.mjs` เพราะทุก test ใช้ผู้ดูแลคนเดียวกันสร้างกิจกรรมเกิน 60 ครั้ง/นาที)
   - ทางเลือก B (Nginx) ไม่อ่าน `_headers` ต้องใส่ header เองใน Nginx
4. **token ยังเก็บใน `localStorage` ต่อ:** ย้ายไป httpOnly cookie ต้องแก้ทั้ง server (ตั้ง cookie, กัน CSRF) และเว็บ คุ้มกว่าที่จะทำพร้อม SSO ในข้อ 1 ระหว่างนี้ CSP คือตัวกัน

## 6 พ.ย. 2569: ทดลองเปิดระบบผ่าน cloudflared tunnel เดียว

เจ้าของโปรเจกต์อยากให้คนอื่นลองใช้ผ่าน `cloudflared tunnel --url` (quick tunnel) ตอนแรกเปิดหน้าเว็บได้ แต่เว็บคุยกับ server ไม่ได้ เพราะเว็บยิง API ไปที่ค่าเริ่มต้น `http://localhost:3000` ซึ่งบนมือถือหมายถึงตัวมือถือเอง

### วิธีที่เลือก

ใช้ tunnel ตัวเดียวชี้ไปที่ Vite (5173) แล้วให้ proxy ของ Vite ส่งต่อ path ของ API ไปที่ 3000 เว็บกับ API จึงอยู่ที่อยู่เดียวกัน และไม่ต้องตั้ง CORS อีกทางคือเปิด tunnel สองตัว ทางนี้ใช้ได้ แต่ต้องตามแก้ URL มากกว่า

ทำแบบนี้ได้เพราะเว็บใช้ `HashRouter` path จริงที่ Vite ต้องตอบจึงไม่ชนกับ path ของ API

### สิ่งที่แก้

| ที่ | การแก้ |
| --- | --- |
| `nu-volunteer-web/vite.config.ts` | `allowedHosts: ['.trycloudflare.com']` และ proxy `^/(auth\|activities\|students\|claims\|templates\|stats\|health\|time)(/\|$)` กับ `/socket.io` (`ws: true`) ไปที่ `http://localhost:3000` |
| `.env` ของ server (ไม่ commit) | `WEB_ORIGIN` = URL ของ tunnel รอบนั้น เพื่อให้ลิงก์ใน QR ถูก และ `TRUST_PROXY=1` |
| ตอนรัน Vite | `VITE_API_URL=<URL ของ tunnel> npm run dev` |
| `CLAUDE.md` | สร้างใหม่สำหรับ Claude Code ไฟล์นี้อยู่ใน `.gitignore` |

ข้อควรรู้:
- **`VITE_API_URL` ต้องเป็น URL เต็มของ tunnel** ใช้ `/api` หรือค่าว่างไม่ได้ เพราะ `remote.ts` ส่งค่านี้เข้า `io()` และ socket.io-client อ่าน path ใน URL เป็นชื่อ namespace
- **`TRUST_PROXY=1` ยังถูก** เพราะ proxy ของ Vite ส่ง `X-Forwarded-For` จาก cloudflared ต่อไปตามเดิม ถ้าเปิด `xfwd: true` ต้องเปลี่ยนเป็น 2
- **ถ้าเพิ่ม controller ที่ path ขึ้นต้นใหม่ ต้องเพิ่มชื่อใน proxy ด้วย**
- **URL ของ quick tunnel เปลี่ยนทุกครั้งที่รัน** ต้องแก้ `WEB_ORIGIN` และ `VITE_API_URL` แล้วเปิด server กับ Vite ใหม่
- **ใช้สำหรับทดลองเท่านั้น** ตอนขึ้นเครื่องจริงให้ Nginx แบ่ง path แบบเดียวกัน

### ปัญหาระหว่างทำ

รอบแรกมือถือขึ้น "โหลดกิจกรรมไม่ได้ ตรวจอินเทอร์เน็ตแล้วเปิดแอปใหม่" สาเหตุคือรายการ path ใน proxy ไม่มี `students` Vite จึงตอบ `/students/...` ด้วย `index.html` แทนการส่งต่อ แล้วเว็บอ่าน HTML เป็น JSON ไม่ได้ ซึ่งไม่ใช่ปัญหาเน็ต

| ตรวจผ่าน tunnel | ก่อนแก้ | หลังแก้ |
| --- | --- | --- |
| `/health`, `/activities`, `/socket.io` | 200 จาก API | 200 จาก API |
| `/students/me/notices` (ไม่ส่ง token) | 200 `text/html` จาก Vite | 401 JSON จาก API |

ไม่ได้รัน `npm test` หรือ e2e เพราะไม่ได้แก้โค้ดของทั้งสองโปรเจกต์

## 6 พ.ย. 2569: ส่งโปสเตอร์เป็น URL และให้ `POST /credits` รับ `reason`

ทำตามแผนงานข้อ 1 และ 2 ด้านล่าง ยังไม่ commit ทั้งสองโปรเจกต์

### 1. โปสเตอร์

- `GET /activities` และ `GET /activities/:id` ส่งรูปที่อัปโหลดเป็น `/activities/:id/poster?v=<เวอร์ชัน>` รูปในตัวเว็บและค่าว่างเหมือนเดิม
- เพิ่ม `GET /activities/:id/poster` ส่ง JPEG พร้อม `ETag` และแคช 1 วัน รับเข้าและเก็บในฐานข้อมูลเหมือนเดิม ไม่แก้โครงสร้างตาราง
- Web: `remote.ts` เติมที่อยู่ของ API ให้จุดเดียว และไม่ส่ง `poster` กลับถ้ายังเป็น URL เดิม ทุก `<img>` จึงไม่ต้องแก้
- เทมเพลตยังส่งตัวรูปเหมือนเดิม

**เปลี่ยนจากแผน:** แผนเดิมใช้ `md5(poster)` เป็นเวอร์ชัน แต่วัดแล้วแพงเกินไป จึงใช้ขนาดไฟล์กับ md5 ของ 8 KB แรก

| โปสเตอร์ 300 KB จำนวน 100 ใบ | เวลาใน SQL ต่อครั้ง | JSON |
| --- | --- | --- |
| `SELECT *` (เดิม) | 152 ms | 39 MB |
| `md5(poster)` (แผนเดิม) | 84 ms | 0.01 MB |
| ขนาด + md5 ของ 8 KB แรก (ที่ใช้) | 6.4 ms | 0.01 MB |

**ข้อแลกเปลี่ยน:** รูปสองใบที่ขนาดเท่ากันทุกไบต์และ 8 KB แรกเหมือนกันจะได้เวอร์ชันเดียวกัน เบราว์เซอร์อาจแสดงรูปเก่าได้ไม่เกิน 1 วัน แล้วจะตรวจ `ETag` และได้รูปใหม่ โอกาสเกิดต่ำมาก จึงไม่ใช้แคชแบบ `immutable`

**ผลวัดผ่าน HTTP จริง** (`dist/main.js` กับ PostgreSQL บนเครื่องเดียวกัน ไม่มีความหน่วงของเครือข่าย)

| รายการ | ผล |
| --- | --- |
| `GET /activities` โปสเตอร์ 20 ใบ | 10.5 KB, 4.6 ms (เดิมประมาณ 8 MB) |
| `GET /activities` โปสเตอร์ 100 ใบ | 52.8 KB, 10.4 ms |
| `GET /activities` พร้อมกัน 50 คำขอ รวม 300 ครั้ง โปสเตอร์ 100 ใบ | median 120 ms, p95 240 ms |

| รูป พร้อมกัน 50 คำขอ รวม 300 ครั้ง | median 108 ms, p95 149 ms |
| รูปที่เบราว์เซอร์มีแล้ว (`If-None-Match`) | 304, 0 ไบต์ |

**1. ~~ส่งโปสเตอร์เป็น URL แทนตัวรูป~~ เสร็จแล้ว**

เจ้าของโปรเจกต์ยืนยันว่าแทบทุกกิจกรรมอัปโหลดรูปเอง ปัญหาจึงเกิดจริง ไม่ใช่กรณีสุดโต่ง และรายการโตตามจำนวนกิจกรรมสะสม

### ข้อสังเกตจากการทดสอบร่วม (รอตัดสินใจ ไม่ได้แก้)

ทดลองเรียก API ตรงแล้วได้ผลตามนี้ หน้าเว็บกันไว้ให้ แต่ server ไม่กัน ต้นแบบก็เป็นแบบเดียวกัน จึงเป็นการตัดสินใจเรื่องกติกา ไม่ใช่บั๊ก

| เรื่อง | ผลที่ได้จริง |
| --- | --- |
| ลงทะเบียนก่อน `opensAt`, ลงทะเบียนกิจกรรมที่ `hidden`, ลงทะเบียนหลังกิจกรรมจบ | `{ result: "ok" }` ทั้งหมด (แก้แล้ว 5 พ.ย. 2569 ได้ 409) |
| ลงทะเบียนหลังหักสิทธิ์ครบ 3 ครั้ง, ลงทะเบียนซ้ำหลังยกเลิกช้า | `{ result: "ok" }` ทั้งคู่ (แก้แล้ว 6 พ.ย. 2569 ได้ 409) |
| แถวลงทะเบียนหลังลงซ้ำจากการยกเลิกช้า | ยังมี `late: true` ทั้งที่ใช้งานอยู่ หน้าเว็บนับสิทธิ์จากแถวที่ `cancelledAt` เท่านั้น จึงยังไม่กระทบ (ไม่เกิดอีกแล้ว 6 พ.ย. 2569 เพราะลงซ้ำไม่ได้) |
| นิสิตที่ไม่ได้ลงทะเบียนอ่านและเขียนแชทกิจกรรม | 200 และ 201 ตรงตามสัญญาที่ให้ "นิสิตทุกคน" แต่หน้าเว็บจำกัดเฉพาะผู้ลงทะเบียน |
| ผู้ดูแลหน่วยงานอื่นอ่านแชท | 200 แต่เขียนไม่ได้ (403) |
| ขนาด `GET /activities` เมื่อมีโปสเตอร์ 300 KB จำนวน 20 ใบ | ประมาณ 8 MB ต่อครั้ง นิสิตโหลดใหม่ทุก 60 วินาทีและทุกครั้งที่กลับมาที่แอป (แก้แล้ว 6 พ.ย. 2569 เหลือ 10.5 KB) |

| `POST /auth/sup` จำกัด 5 ครั้ง/นาที/IP | หน้าเว็บแสดงข้อความให้รอถูกต้อง แต่ผู้ดูแลหลายคนหลัง NAT เดียวกันอาจติดพร้อมกัน |
